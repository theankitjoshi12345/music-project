# P#8 — User Testing: Validating Your Prototype

**Due:** Monday, October 19, 2026, 11:55 PM

## Overview

Before investing weeks of development time, validate whether the design makes sense to real users. In P#7, the team created static screens showing how a user completes one task. In P#8, put those screens in front of real users and observe what happens.

Core question: When a user from the target segment sees the screens, can they figure out what to do? Identify hesitation, confusion, and delight.

## Protocol: Wizard of Oz Testing

The team acts as the computer: the user says what they would tap or click, and the team presents the next screen.

At least two team members must attend each session:

| Role | Responsibility |
| --- | --- |
| Facilitator | Runs the session, shows screens, and asks questions. Does not help unless the user is completely stuck. |
| Observer | Takes detailed notes; watches face/body language; times hesitations; captures quotes. |

With three or more available members, add a dedicated note-taker so the observer can focus on watching.

## Before Each Session

1. Recruit **3–5 users** from the target segment(s) defined in P#7. Do not recruit teammates; do not use friends unless they genuinely fit the segment.
2. Prepare screens in order. Images on a tablet or laptop are recommended; a Figma/InVision clickable prototype or printed screens are also acceptable.
3. Write the task prompt exactly as it will be read. Example: “Imagine it’s 7 PM on a weekday. You’re home, you’ve had a long day, and you need to figure out what to make for dinner. Show me how you’d use this app to solve that.”
4. Prepare a digital or printed observation sheet for every session.

## Session Script

### 1. Introduction (2 minutes)

Say:

> Thanks for helping us today. We’re designing an app and want to see if our design makes sense. I’m going to show you some screens and ask you to complete a task.
>
> We’re testing the design, not you. There are no wrong answers. Please think out loud—tell me what you’re looking at, what you’re thinking, and what you’d tap. I’ll act as the computer: tell me what you’d tap and I’ll show you what happens. I won’t help unless you’re completely stuck. If it’s confusing, that’s useful information for us. Any questions before we start?

### 2. Context setting (1 minute)

Read the task prompt and set the scene so the user is in the intended mindset.

### 3. Task (5–10 minutes)

Show the first screen and ask: “What do you see? What would you do?”

- Do not guide the user. If they hesitate or take a wrong path, wait and observe.
- Prompt think-aloud behavior: “What are you thinking?”
- Ask clarifying questions: “You hesitated there—what were you looking for?”
- If the user is completely stuck (30+ seconds of confusion), provide a hint and document the intervention.

### 4. Post-task questions (5 minutes)

- How was that experience?
- Was anything confusing?
- What did you expect to happen that did not?
- Would you use something like this? Why or why not?
- What is missing?

### 5. Wrap-up (1 minute)

Thank the user and provide any promised compensation.

## Observation Form

Use anonymous IDs only (for example, “User 1”); do not include real names in the report.

| Element | Notes to capture |
| --- | --- |
| User ID | Anonymous identifier |
| Segment | Behavioral segment fit |
| Date/time | Session date and time |
| Task completion | Yes / Partial / No |
| Time to complete | Duration |
| Hesitation points | Screen and moment of pause/confusion |
| Wrong turns | Non-working item the user tried to tap or use |
| Questions asked | Questions during the test |
| Verbal reactions | Positive, negative, and confused quotes |
| Suggestions | Missing or requested changes |
| Would use? | Yes / Maybe / No, with reason |

## Synthesis

After all 3–5 sessions, identify patterns:

- Multiple users hesitated: design problem.
- Multiple users misunderstood something: mental model mismatch.
- Users expected something unavailable: missing feature or unclear affordance.
- Users loved something: preserve it.

## Tips

- Do not defend or explain the design during testing; confusion is data.
- Silence is valuable: wait when users hesitate.
- Recruit outside the team’s immediate social circle when possible.
- With consent, video/screen recording is optional and valuable for later review.
- Three users commonly reveal most major problems; test 3–5 people from the target segment.
